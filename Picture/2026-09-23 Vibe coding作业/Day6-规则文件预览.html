项目规则（AGENTS.md）

我每天会把「今日任务清单」整块发给你，那是我今天要做的全部内容。请严格按下面的规则配合我，不要做清单以外的事。

一、任务边界（最重要）

1. 收到我的任务清单后，**这份清单就是今天唯一的任务范围**，只做清单里写的事。
2. 不做清单以外的工作：不建多余的文件、不写清单没提的功能、不顺手优化已有代码。你觉得可以改得更好，先跟我说一句，等我点头。
3. 不提前做以后的天数。只有我把某天的清单发给你、并明确说「现在开始做 Day X」，才允许动那天。
4. 拿不准是否在范围内，先问我，不要猜。

二、交互式推进

1. 收到清单后，先只给我今天的执行计划：按什么顺序做、每步怎么做、哪些要我自己动手。**写完停下，等我确认。**
2. 确认后**一次只做一个步骤**，绝不连着往下做。
3. 每步做完立刻停下，告诉我三件事：做了什么、改了哪些文件、怎么验证（附我能亲眼确认的结果）。
4. 然后**停下等我回复「进入下一板块」**。我没说这四个字，你就不要继续。
5. 「进入下一板块」只对当前这一步有效，不代表可以一路做到收尾。

三、人机分工

1. 需要我人工操作的（注册账号、点按钮、装软件、截图等）：不要替我做，也不要假装已完成。只告诉我：这步在干什么、一二三步怎么做、做完我该看到什么、容易踩什么坑，然后停下等我。
2. 需要你生成的内容（写文档、建文件、写代码）：**等我说了再做**，不要在我刚说「开始吧」时就把整天的东西生成出来。
3. 需要拍板的地方（选方案、起名字、定风格），把选项和各自代价列给我选，不要自己决定。
4. 验证结果要我能亲眼确认（页面能打开、文件能看到、命令有输出），不接受「已经完成了」这种口头结论。

四、讲清楚环节（我是来学的）

1. 每个步骤开始前，先告诉我：它在整个作品里是什么位置、为什么现在做、做完会变成什么样。
2. 每步用「做了什么 → 结果 → 为什么」讲明白，不要只给结果。
3. 我不懂的概念（命令、报错、术语、配置），一两句话解释清楚，不要默认我会。
4. 报错时先告诉我错在哪、可能什么原因、打算怎么修，我同意后再动手。不要输出教程式长文。

五、Git 与提交

1. 我授权你代为执行 git 提交和推送，但**提交前必须先列出**本次会改动哪些文件、每个文件属于哪天的任务，等我确认后再提交。
2. commit 信息格式：`Day X｜一句话说明`。
3. 密钥、`.env`、数据库连接串永远不进代码、不进提交。
4. 一天的任务全部做完、我核对完文件清单之后才提交，中途不要边做边提交。

六、当日收尾

1. 我说「今天做完了」之后，请你逐条对照清单里的「完成标准」，输出一张表：完成标准 / 状态（已完成·部分完成·未完成）/ 证据（文件、页面、命令输出）。
2. 核对必须诚实，没做完、做了一半、跳过没做的，直接标出来并说明原因，不要为了凑「全部完成」而模糊处理。
3. 有未完成项时，告诉我还差什么、接不接着做，**由我决定**，不要自己往下做。
4. 全部完成时，按清单的「收尾指令」整理当天成果，提醒我该交哪张截图、该在群里回什么。

七、出问题的时候

1. 我要求撤销时，用安全回退（`git revert`，保留历史），禁止 `git reset --hard` 和强制推送。
2. 回退前先和我确认恢复到哪个提交，回退后列出当前状态让我核对。
3. 同一个操作反复失败时停下来报告，说清楚试了什么、报什么错、你判断的原因，不要循环重试。

附 6. commit 信息规范（2026-09-17 追加，Day 2 起生效）

**从 Day 2 开始，所有提交一律按这个格式：标题一行 + 正文两行。**

Day X｜一句话说清这次做了什么

改了什么：<对已有文件做了哪些修改>
加了什么：<新增了哪些文件>

**细则：**

1. **标题**固定以 `Day X｜` 开头（X 是当天的天数），后面跟一句话。全角竖线 `｜`，不是 `|`。
2. **正文两行**各用「改了什么：」「加了什么：」起头，写清楚具体是哪些文件、做了什么。
3. 某天**没有**新增文件时写「加了什么：无」；**没有**修改已有文件时写「改了什么：无」。两行都不要省略。
4. 补交、修补类提交同样照此格式，天数写当天。
5. 提交信息里**不写**任何密码、密钥、邮箱等敏感内容。

**执行样例（Git 命令）：**

git commit -m "Day 3｜首页加上顶部导航栏" \
           -m "改了什么：index.html 增加导航区、调整了页面边距" \
           -m "加了什么：css/style.css"

**验收自检**：提交后用 `git log -1` 看一眼，标题应以 `Day ` 开头，正文应能看到「改了什么：」和「加了什么：」两行。

附 7. 改完必须报「未提交改动」（2026-09-23 追加，Day 6 起生效）

**一句话**：只要动了文件，就要**主动**告诉子豪"现在有几处改动还没提交"，不用等他问。

**为什么加这条（防的是什么）**：

• 已经真实发生过两次：文件改了，但子豪没说「提交」，改动就**一直留在文件里、静静地未被记录**。等到下一轮一起提交时，**提交信息漏掉了上一轮的内容**（只能靠 `git commit --amend` 补救）。
• 关键认知：**"改完了" ≠ "提交了"** —— 改动只写在文件里，git 只有在你发话后才为它存档。**没有提交的改动，回退时会一起消失，也说不清它是哪次做的。**
• 所以这条规则防的是：**改动被遗忘在文件里，最终丢失或说不清来源。**

**具体怎么做（每次改完文件立刻执行）**：

1. 用 `git status --short` 看一眼当前工作区，把**所有未提交的改动**（不只本轮新的）列出来。
2. 主动在回复里加一行醒目提示，格式建议：

```

⚠️ 当前有 N 处改动尚未提交，等你确认后再提交打包

```

3. 如果**上一轮就有未提交的改动**，必须在这一行里一并写出来（写明是"上一轮遗留"），**不能只讲本轮新增的**。
4. 列提交清单时，**把工作区里所有未提交改动全部列出**，逐个标明属于哪天的任务。
5. 不允许"攒改动"：如果连续两轮都有改动，第一次改完就要提醒一次，不能等第二次才说。

**与第五章的分工**：

• 第五章第 1 条管的是「**提交时**：先列清单等我确认」
• 本附 7 管的是「**提交前**：任何时刻都要让我知道筐里有东西」
• 两条配合，确保"未提交的改动"永远在明面上。

附 8. 提交前必过清单 · 检查项版（2026-09-23 追加，Day 6 余力加练）

附 7 是**叮嘱**（"记得报备"），附 8 是**验收表** —— 换成任何人（队友、以后接手的朋友、未来的自己）都能照着核一遍的写法：**每一条都有动作、有命令、有"看到什么才算过"**。

**每次提交前，从上往下逐条打勾：**

| # | 检查动作（照做即可） | 通过标准（看到什么才算过） | 为什么这么做（它在防什么） |

|---|---|---|---|

| 1 | 跑 `git status --short` | **输出为空** → 没有未提交改动，可以进入提交流程 | **你不可能保护你不知道存在的东西。** 先看清"筐里有什么"，再决定做什么 |

| 2 | 若第 1 步**有**输出：逐个看文件名 | 每一个输出行都**能说出"它属于哪天的任务"**；说不出的先问，不要提交 | 防"**张冠李戴**"：上一轮的遗留混进这一轮。说得出 = 心里有数；说不出 = 有东西脱离掌控 |

| 3 | 跑 `git diff --stat` | 改动范围符合任务要求。任务写着"只允许追加"时，**deletions 必须为 0** | 防"**手滑改多了**"。数字不会撒谎 —— "我保证没删"是口头结论，`deletions: 0` 是硬证据 |

| 4 | 写提交信息时，回头看**上一轮**有没有遗留改动 | 若有，**必须写进信息里**并标注"（含上一轮遗留）" | ⭐ **唯一查"记忆"而非查文件的一条**：`git status` 看不出改动是哪一轮做的，这个信息只存在于对话里，必须由人来补 |

| 5 | 提交后跑 `git log -1` | 标题以 `Day ` 开头，正文能看到「改了什么：」「加了什么：」两行 | 防"**格式写漏**"。此刻**还来得及改**（未推送可 `--amend`）；推送后再发现就只能补发新提交 |

| 6 | 推送后跑 `git ls-remote origin` | 云端 `refs/heads/main` 的哈希 **= 本地最新提交哈希** | 防"**假推送**"。本地说"成功"= 邮局说"我收了"；云端哈希对上 = 打电话问到"那边真收到了" |

**这六条为什么按这个顺序**：

提交前                 →   提交中            →   提交后
① 看清筐里             ④ 补上记忆里的遗留   ⑤ 验信息格式
② 逐个认领                                 ⑥ 验云端收货
③ 看改了多少
• **前三条查"现状"**（命令告诉你）
• **第四条补"记忆"**（只有人能补）
• **后两条验"结果"**（信息对不对 + 送到了没）

**用法说明**：

• 六条**按顺序**做，前一条不过就别进下一条。
• 第 1、2 条如果卡住，说明**有东西没归位** —— 这时先问我，不要擅自提交。
• 这份清单不只给 AI 用：**子豪自己提交、或将来跟队友协作时**，同一张表照样能核。
• 最要紧的其实是**第 3 条和第 6 条**（一个防手滑、一个防假推送）；其余四条偏"确认心安"，但"确认心安"不是浪费 —— 漏一次就要多花一次 `--amend` 的功夫。

**它和附 7 的关系**：附 7 管「**随时提醒**」（过程中），附 8 管「**提交前把关**」（终点前）。两条合起来，等于给"改动会不会丢"上了双保险。
