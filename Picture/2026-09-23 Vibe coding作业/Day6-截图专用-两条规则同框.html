① Day 1 原有规则 · 一字未改

一、任务边界（最重要）

1. 收到我的任务清单后，这份清单就是今天唯一的任务范围，只做清单里写的事。
2. 不做清单以外的工作：不建多余的文件、不写清单没提的功能、不顺手优化已有代码。你觉得可以改得更好，先跟我说一句，等我点头。
3. 不提前做以后的天数。只有我把某天的清单发给你、并明确说「现在开始做 Day X」，才允许动那天。
4. 拿不准是否在范围内，先问我，不要猜。
② 今日追加 · 附 7 + 附 8

附 7. 改完必须报「未提交改动」（2026-09-23 追加，Day 6 起生效）

一句话：只要动了文件，就要主动告诉子豪"现在有几处改动还没提交"，不用等他问。

为什么加这条（防的是什么）：

• 已经真实发生过两次：文件改了，但子豪没说「提交」，改动就一直留在文件里、静静地未被记录。等到下一轮一起提交时，提交信息漏掉了上一轮的内容（只能靠 git commit --amend 补救）。
• 关键认知："改完了" ≠ "提交了" —— 改动只写在文件里，git 只有在你发话后才为它存档。没有提交的改动，回退时会一起消失，也说不清它是哪次做的。
• 所以这条规则防的是：改动被遗忘在文件里，最终丢失或说不清来源。

具体怎么做（每次改完文件立刻执行）：

1. 用 git status --short 看一眼当前工作区，把所有未提交的改动（不只本轮新的）列出来。
2. 主动在回复里加一行醒目提示，格式建议：

`

⚠️ 当前有 N 处改动尚未提交，等你确认后再提交打包

`

3. 如果上一轮就有未提交的改动，必须在这一行里一并写出来（写明是"上一轮遗留"），不能只讲本轮新增的。
4. 列提交清单时，把工作区里所有未提交改动全部列出，逐个标明属于哪天的任务。
5. 不允许"攒改动"：如果连续两轮都有改动，第一次改完就要提醒一次，不能等第二次才说。

与第五章的分工：

• 第五章第 1 条管的是「提交时：先列清单等我确认」
• 本附 7 管的是「提交前：任何时刻都要让我知道筐里有东西」
• 两条配合，确保"未提交的改动"永远在明面上。

附 8. 提交前必过清单 · 检查项版（2026-09-23 追加，Day 6 余力加练）

附 7 是叮嘱（"记得报备"），附 8 是验收表 —— 换成任何人（队友、以后接手的朋友、未来的自己）都能照着核一遍的写法：每一条都有动作、有命令、有"看到什么才算过"。

每次提交前，从上往下逐条打勾：

#
检查动作（照做即可）
通过标准（看到什么才算过）
为什么这么做（它在防什么）
1
跑 git status --short
输出为空 → 没有未提交改动，可以进入提交流程
你不可能保护你不知道存在的东西。 先看清"筐里有什么"，再决定做什么
2
若第 1 步有输出：逐个看文件名
每一个输出行都能说出"它属于哪天的任务"；说不出的先问，不要提交
防"张冠李戴"：上一轮的遗留混进这一轮。说得出 = 心里有数；说不出 = 有东西脱离掌控
3
跑 git diff --stat
改动范围符合任务要求。任务写着"只允许追加"时，deletions 必须为 0
防"手滑改多了"。数字不会撒谎 —— "我保证没删"是口头结论，deletions: 0 是硬证据
4
写提交信息时，回头看上一轮有没有遗留改动
若有，必须写进信息里并标注"（含上一轮遗留）"
⭐ 唯一查"记忆"而非查文件的一条：git status 看不出改动是哪一轮做的，这个信息只存在于对话里，必须由人来补
5
提交后跑 git log -1
标题以 Day 开头，正文能看到「改了什么：」「加了什么：」两行
防"格式写漏"。此刻还来得及改（未推送可 --amend）；推送后再发现就只能补发新提交
6
推送后跑 git ls-remote origin
云端 refs/heads/main 的哈希 = 本地最新提交哈希
防"假推送"。本地说"成功"= 邮局说"我收了"；云端哈希对上 = 打电话问到"那边真收到了"

这六条为什么按这个顺序：

提交前                 →   提交中            →   提交后
① 看清筐里             ④ 补上记忆里的遗留   ⑤ 验信息格式
② 逐个认领                                 ⑥ 验云端收货
③ 看改了多少
• 前三条查"现状"（命令告诉你）
• 第四条补"记忆"（只有人能补）
• 后两条验"结果"（信息对不对 + 送到了没）

用法说明：

• 六条按顺序做，前一条不过就别进下一条。
• 第 1、2 条如果卡住，说明有东西没归位 —— 这时先问我，不要擅自提交。
• 这份清单不只给 AI 用：子豪自己提交、或将来跟队友协作时，同一张表照样能核。
• 最要紧的其实是第 3 条和第 6 条（一个防手滑、一个防假推送）；其余四条偏"确认心安"，但"确认心安"不是浪费 —— 漏一次就要多花一次 --amend 的功夫。

它和附 7 的关系：附 7 管「随时提醒」（过程中），附 8 管「提交前把关」（终点前）。两条合起来，等于给"改动会不会丢"上了双保险。
